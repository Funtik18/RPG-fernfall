# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Fire" is a Unity 6 (6000.5.7f1) turn-based strategy RPG, bootstrapped from Unity's URP (Universal Render Pipeline) template. The project is in an early skeleton stage: the repo was seeded with several third-party assets/plugins, and project-specific code so far consists of a "Scroll" record UI wireframe (see below) and a `Test_SyntyOnGrid` vertical slice proving out TBSF movement/combat on a throwaway flat grid (see `TestGridUnit`). There is still no turn manager, save system, or general unit/character system — the vertical slice is a test harness, not the target architecture.

Target platforms are PC and consoles. Gamepad support is first-class from day one, not a port-time addition — all input goes through Unity's Input System (not legacy Input), with parallel KBM and Gamepad control schemes defined side-by-side for every input surface (e.g. the tactical camera's `Camera` action map). UI must remain fully navigable without a mouse.

Battle maps are 3D with elevation, bridges, and stairs. `Test_SyntyOnGrid` now has a small elevation test area (two ground platforms at different heights joined by a single bridge cell-pair over an impassable water gap) proving this out — see the `HeightAwareGridBuilder`/`AttackZoneCalculator` note below. Any system built against flat-grid assumptions (camera focus height, line of sight, movement cost) should either be written elevation-aware from the start (e.g. the tactical camera's focus point raycasts down to a `Ground` layer for its height rather than assuming Y=0) or explicitly flagged as flat-only debt.

Design/narrative docs (e.g. the authoritative Scroll record format) live outside this repo at `E:\FireObsidian\Fire\Docs` — not checked in here.

## Commands

There is no CLI build/lint pipeline (no `.github/workflows`, no build scripts). Building and running still goes through the Unity Editor (6000.5.7f1) directly — open the project in Unity Hub and use Play Mode / File > Build Settings.

EditMode tests now exist under `Assets/_Project/Tests/EditMode` (`Fire.Tests.EditMode.asmdef`), covering the Scroll data/UI logic, `TacticalCameraController` (`NearestDiagonal` including exact-midpoint tie-breaking, and the `ZoomVerticalValue` per-zoom-level table), `AttackZoneCalculator` (via `FakeCell`/`FakeUnit` test doubles under `Tests/EditMode/TestSupport`), and TBSFramework's own combat-damage formula (`Tests/EditMode/ThirdPartyDependencyPinning` — see the pinning-vs-correctness testing rule below). Run them headlessly from the command line:
```
"<UnityInstallPath>/Editor/Unity.exe" -batchmode -nographics -projectPath "<repo>" -runTests -testPlatform EditMode -testResults "<repo>/Temp/EditModeTestResults.xml" -logFile "<repo>/Temp/EditModeTestRun.log"
```
Two gotchas that cost real debugging time getting this working: (1) **do not add `-quit`** — `-runTests` manages its own exit, and combining it with `-quit` makes the Editor quit right after the initial asset import, before the test runner ever executes (no compile errors, no results file, exits 0 as if nothing was wrong). (2) The `-testResults` path is often *not* where results actually land — Unity additionally (and sometimes *only*) writes to `%USERPROFILE%\AppData\LocalLow\DefaultCompany\<ProductName>\TestResults.xml`; check both locations rather than assuming the `-testResults` argument was honored.

No PlayMode test suite exists yet. `TestGridUnit`/TBSF combat integration and the `TacticalCameraController` Cinemachine rig are exercised via manual Play Mode verification (through Unity MCP tooling), not automated PlayMode tests — they're tightly coupled to a live scene/TBSF grid state that wasn't worth standing up as EditMode tests.

The one custom tool is an Editor menu command:
- **Tools > Fire > Build Scroll Wireframe Scene** — runs `ScrollWireframeBuilder.Build()`, which procedurally regenerates `Assets/_Project/Scenes/UI_ScrollWireframe.unity` and `Assets/_Project/Prefabs/UI/Scroll/RecordListItem.prefab` in code. Re-running it **overwrites** both, so don't hand-edit that scene/prefab expecting changes to survive.

## Architecture

### Where project code lives

All project-specific code is under `Assets/_Project`; everything else at the `Assets/` root is a third-party dependency and should generally not be modified:
- `Assets/TBSFramework` — crookedhead's TBS Framework (grid/cell/unit/AI scaffolding for turn-based games). Ships its own asmdefs and bundled example projects (ClashOfHeroes, TilemapExample, etc.) under `Examples/`.
- `Packages/com.arongranberg.astar` — A* Pathfinding Project Pro, embedded as a local package. Includes a `TurnBased/` module (`BlockManager`, `SingleNodeBlocker`) intended for turn-based movement blocking.
- `Assets/Synty`, `Assets/Casual Game Sounds U6`, `Assets/Fantasy Sfx`, `Assets/TextMesh Pro`, `Assets/URPDefaultResources`, `Assets/Plugins` (includes Odin Inspector / Sirenix) — asset packs and plugins. Note the Synty "Meadow Forest" pack is not its own top-level folder — the Asset Store product is "POLYGON – Meadow Forest – Nature Biomes", so it imports as `Assets/Synty/PolygonNatureBiomes/PNB_Meadow_Forest`.

The A* Pathfinding package is still an integration-pending dependency, not yet an architectural pillar — no project code references it. TBSFramework is now integrated (see `Assets/_Project/Scripts/Gameplay/TestGrid/TestGridUnit.cs` and the `Test_SyntyOnGrid` scene): a project `Unit` subclass wired to standard TBSF prefabs (`MoveAbility`/`AttackAbility`/`AttackRangeHighlightAbility`, a `Square`-shaped `Cell`, `UnityGridController`/`RegularCellManager`/`UnityUnitManager`/`UnityPlayerManager`), not a fork or modification of the framework itself. When wiring up further movement/combat, follow this same pattern rather than building from scratch — see the TBSF animation note below for one concrete hook point.

Most of `Assets/_Project` still has no `.asmdef` and compiles into the default `Assembly-CSharp` / `Assembly-CSharp-Editor` assemblies. Three folders are the exception, carved out specifically so EditMode tests could reference their types (a plain `"Assembly-CSharp"` entry in another asmdef's `references` is **not** a supported way to depend on the default assembly — Unity silently fails to resolve it with no clear error beyond "type not found"; the only reliable fix is giving the tested code its own asmdef): `Assets/_Project/Scripts/UI/Scroll/Fire.UI.Scroll.asmdef`, `Assets/_Project/Scripts/Camera/Fire.Camera.asmdef`, and `Assets/_Project/Scripts/Gameplay/TestGrid/Fire.Gameplay.TestGrid.asmdef`. If you add code to any of these folders, it now compiles into that asmdef instead of `Assembly-CSharp` — cross-references from `Assembly-CSharp` code still work fine (predefined assemblies auto-reference every asmdef), but code in these folders can no longer implicitly see the rest of `Assets/_Project` and needs its dependencies added explicitly to the asmdef's `references`. Practical GUID reference for wiring a new one of these: TBSF's Unity-layer asmdef (`com.crookedhead.tbsf.unity`) is GUID `ba1d260f9e69eb6409c598826f52f7b9`, its Common (engine-independent) layer (`com.crookedhead.tbsf.common` — `ICell`, `IUnit`, `CombatComponent`, etc.) is GUID `73e792cf0fd01b3438c14a3a994dd2ce`.

**Automated tests cover logic, never render — visual correctness stays on screenshot verification, always.** This formalizes, one level up, the same principle behind the `GetPropertyBlock`/`SampleAnimationClip` finding above: a test that reads `material.color`, an alpha value, or any other rendered-state value back through code inherits the exact same unreliability as an MCP tool doing the same readback — it can go green over a visibly broken screen, which is worse than no test at all (a passing suite actively signals "verified" when it wasn't). Automated coverage in this project is scoped to pure logic only — math, data transformations, formulas over plain C# types — never rendering, materials, shaders, blending, or "does this look/feel right." `Assets/_Project/Tests/EditMode/Gameplay/TestGrid/AttackZoneCalculatorTests.cs` is the concrete example: it tests the `HashSet<ICell>` math (self-cell exclusion, zone/reachable disjointness), but the "purple cells" symptom from the same investigation was never testable this way in principle — it was a `Cell.Visual` alpha blend over a specific material's base color, confirmed only by disabling render layers live in Play Mode and reading the result off a screenshot. When a bug's proposed fix would require a test to assert on a color, alpha, blend mode, or "smoothness," that's the signal it belongs in manual/MCP screenshot verification instead, not in the EditMode suite.

**"Don't write tests against TBSFramework" means don't test whether TBSF's internal logic is *correct* — it doesn't mean "never call TBSF code from a test."** The package maintainer owns TBSF's correctness (pathfinding internals, framework-internal data structures) — that's out of scope, full stop. But a handful of TBSF methods are direct, load-bearing inputs to this game's own balance — e.g. `CombatComponent.CalculateDamageDealt`/`CalculateDamageTaken` (`Tests/EditMode/ThirdPartyDependencyPinning/CombatComponentDamageFormulaPinningTests.cs`), which `TestGridUnit` inherits unmodified. Tests against those exist as **pinning tests**, not correctness tests: they assert today's *observed* behavior so that a future TBSFramework package update silently changing the formula turns the suite red immediately, instead of the change surfacing as an unexplained balance shift found by playtesters after release. A pinning-test failure after a package upgrade is never "go fix TBSF" — it's "decide, deliberately, whether the project's balance assumptions still hold against the new behavior, then update the pinned expectation." Keep pinning tests physically separate from project-logic tests (their own folder, a header comment stating why the test exists) so nobody mistakes one for the other later.

**Dependency-first rule:** before writing new functionality from scratch, check whether an already-integrated package covers it. The project ships TBSFramework (grid/cell/unit/AI scaffolding), A* Pathfinding Pro (including its `TurnBased/` module), Odin Inspector (editor/inspector tooling, serialization), and Synty asset packs. Prefer wiring up an existing backend over hand-rolling an equivalent. If nothing fits, say so explicitly rather than silently building a parallel implementation.

**TBSF has no opinion on animation.** `Unit` moves its transform directly (`MoveTowards` inside `UnityMoveComponent.MovementAnimation`) and only fires structural events (`UnitLeftCell`/`UnitEnteredCell`/`UnitMoved`) — there's no Animator hookup anywhere in the framework. The pattern for bridging any unit action into an Animator (walk, attack, death, hit reaction, ...) is the same: override the relevant `virtual` method on your own `Unit` subclass (e.g. `MovementAnimation`) and drive the Animator around the `base` call. `TestGridUnit` does exactly this for walk/idle — copy that shape for combat animations rather than rediscovering it.

**General principle: reading runtime rendering/animation state back through an Editor-tooling API is not trustworthy — when in doubt, verify with a screenshot instead of a value readback.** Two confirmed cases so far, both cost significant time before the pattern was recognized:
- `AnimationMode.SampleAnimationClip` does not run the full Humanoid retargeting pipeline and can report values with no relationship to actual runtime playback — in one case it reported a physically impossible ~900-1950°/sec on a clip that plays back perfectly smoothly, costing a full session chasing a "corrupted mocap" theory that wasn't real. To check whether a Humanoid clip/transition is actually smooth, record real per-frame deltas from `Animator.GetBoneTransform(HumanBodyBones.*)` while the clip plays live in Play Mode (a temporary `MonoBehaviour` sampling in `Update()`) — never from an Editor-only sampling API.
- `Renderer.GetPropertyBlock()` called from Unity MCP's `RunCommand` tool does not reliably reflect what `SetPropertyBlock()` (including via `RendererHighlighter.Apply()`) actually applied. Chased this as a real bug for a long time: `Cell.MarkAsReachable()` reported `Task.RanToCompletion`, the `Highlighter`'s serialized `_renderer`/`_color` fields were all confirmed correct via `SerializedObject`, a raw inline `SetPropertyBlock`+`GetPropertyBlock` roundtrip in the same script worked fine — yet reading the property block back through a `RendererHighlighter` call, from EditMode, from Play Mode, after a guaranteed-correct-field-order `Awake` (inactive→set fields→activate trick), always read back `(0,0,0,0)`. A `Unity_SceneView_CaptureMultiAngleSceneView` screenshot immediately after showed the highlighting had in fact applied perfectly. Root cause unconfirmed in both cases (never fully explained) — the point isn't the specific API, it's the pattern: **don't trust a runtime rendering/animation value read back through Editor-tooling code as a pass/fail signal; trust a screenshot.**

**A `CinemachineCamera` with only a Body-stage component (e.g. `CinemachineOrbitalFollow`) does not aim itself.** `OrbitalFollow` positions the camera correctly around its `Follow` target at any orbit angle, but without a separate Aim-stage component (`CinemachineRotationComposer` or equivalent) the camera's rotation never updates — it stays frozen at whatever rotation the GameObject happened to have, so it only *looks* correct at whichever single angle matches that frozen rotation by coincidence. This is exactly what happened building the `Test_SyntyOnGrid` tactical camera: it appeared to work at the default 0° test angle and broke (targets off-screen, `transform.forward` never changing) at every other rotation. Diagnose a suspect orbital rig by checking `Vector3.Dot(cam.transform.forward, (lookAtTarget.position - cam.transform.position).normalized)` at a *non-default* angle — it should be ~1.0; if it's unrelated to the angle, the Aim stage is missing. Separately, `CinemachineOrbitalFollow.TrackerSettings.PositionDamping` in `WorldSpace` binding mode damps X/Y/Z independently and is not meant for circular orbital motion — leave it at zero and let any easing happen at the input-axis level (e.g. `InputAxis.Recentering`, or a `SmoothDamp` in your own controller) instead.

**`CinemachineOrbitalFollow.RecenteringTarget` defaults to `TrackingTarget`, which silently overwrites `HorizontalAxis.Center` every frame on top of any custom axis-positioning logic — the same class of bug as TBSF's `MarkAsHighlighted`/`MarkAsPath` default behavior fighting a custom highlight system (see above): a framework doing something by default that conflicts with custom logic unless explicitly turned off.** `TacticalCameraController.HandleRotation()`'s snap-to-diagonal-on-release feature sets `OrbitalFollow.HorizontalAxis.Center = NearestDiagonal(...)` and enables `Recentering` — this looked correct in isolation (`NearestDiagonal` itself is mathematically exact, confirmed by fuzz-testing it against an independent reference implementation across the full ±360° range with zero mismatches) but the camera always snapped to the *same* orientation regardless of the starting angle. Root cause confirmed by reading `CinemachineOrbitalFollow.MutateCameraState` directly: whenever `HorizontalAxis.Recentering.Enabled` is true, it calls `UpdateHorizontalCenter()` **every frame**, which recomputes `Center` from `RecenteringTarget` — the default (`TrackingTarget`) sets it to the angle behind the Follow target's current `forward`, unconditionally overwriting whatever `Center` a custom script just set, one frame after it was set. Since the rig's Follow target (`CameraFocus`) has a static, never-rotating transform, this recomputed to the same constant value every time, regardless of `NearestDiagonal`'s (correct) output — confirmed empirically: forcing `RecenteringTarget = AxisCenter` (the one setting where `UpdateHorizontalCenter` leaves `Center` alone, per its own `AxisCenter` case doing nothing unless `BindingMode == LazyFollow`) immediately made the same test converge correctly to all 4 target diagonals (45/135/-135/-45) from 8 different starting angles spanning every quadrant. Fixed in both places: the scene asset (`RecenteringTarget: 2` → `0` on `Test_SyntyOnGrid`'s `TacticalCamera`) and defensively in code (`TacticalCameraController.OnEnable()` now force-sets `OrbitalFollow.RecenteringTarget = ReferenceFrames.AxisCenter`), since re-adding or resetting this component in the Inspector would silently restore the conflicting default. **Rule: any script that drives `InputAxis.Center`/`Recentering` directly on a `CinemachineOrbitalFollow` must explicitly set `RecenteringTarget = AxisCenter` first** — otherwise the component's own per-frame recentering-target logic owns `Center`, not your script, and the conflict is invisible until you test more than one starting angle.

**TBSF's grid is a strict 2D coordinate graph — height is purely decorative unless you add it yourself.** Confirmed by reading the framework source directly, not assumed: `Cell.WorldPosition` is a bare `transform.position` alias (no Y constraint anywhere), but `SquareHelper.GetDistance`/`GetNeighbours` (backing `ICell.GetDistance` and `Unit.GetAvailableDestinations`'s pathfinding graph) work purely off integer `GridCoordinates` — no raycast, no line-of-sight, no obstruction check, completely height-agnostic. `MoveComponent.GetMovementCost(source, destination)` likewise only returns `destination.MovementCost`; the `source` parameter is accepted but unused, so climbing vs. descending cost the same by default (the extension point, if that's ever wanted, is `Unit.GetMovementCost` — `virtual`, override it the same way `TestGridUnit` already overrides `MovementAnimation`). `CombatComponent.IsUnitAttackable` is a pure `GetDistance(...) <= AttackRange` check — same Manhattan/height-agnostic distance, no LOS. One real structural consequence: `RegularCellManager.GetCellAt` keys strictly by `(x,y)`, one `Cell` per coordinate — a bridge that passes **over** another walkable path (same X/Z footprint, different Y) can't be represented; a bridge over an impassable gap (water/chasm, i.e. no `Cell` placed under it at all) works fine and is the pattern `Test_SyntyOnGrid`'s elevation area uses. Movement itself needs no elevation-awareness work at all — `UnityMoveComponent.MovementAnimation` already does `Vector3.MoveTowards` through each path cell's *actual* `WorldPosition` (full 3D, no flat-Y assumption), so a unit already walks a ramp/step profile correctly the moment the cells themselves sit at the right heights.

**Height-aware grid placement lives in project code, not the framework.** TBSF's own `RectangularSquareGridGenerator` (`Assets/TBSFramework/Editor/GridGenerators`) hardcodes `Y=0` for every cell in its 3D branch — it has no elevation concept at all. `Assets/_Project/Editor/TestGrid/HeightAwareGridBuilder.cs` is the project-side replacement pattern: for each intended `(x,y)`, raycast straight down against a `Ground`-layer collider and place the cell at the hit height; a coordinate with no ground hit (a gap/water column) simply gets no `Cell` placed there at all — no framework changes needed, since a missing coordinate is already treated as impassable by `GetCellAt`/`GetNeighbours`. Keep the actual walkable-surface collider **decoupled** from decorative terrain meshes (author your own precisely-placed/sized `BoxCollider` on the `Ground` layer rather than trusting a Synty prop's shipped collision mesh) — far more predictable than reverse-engineering an asset's exact bounds.

**A second, independent highlight zone (e.g. attack range) needs its own renderer — it cannot reuse `Cell`'s 4 highlighter slots.** `Cell` ships exactly 4 fixed, private `List<Highlighter>` fields (`_unMarkFn`/`_markAsHighlightedFn`/`_markAsReachableFn`/`_markAsPathFn`), all wired in the `TestSquareCell` prefab to `RendererHighlighter` instances targeting the **same** `Visual` renderer's `MaterialPropertyBlock` — a 5th zone sharing that renderer would just overwrite whichever zone's color was applied last. The pattern used for the attack-range overlay (`Assets/_Project/Scripts/Gameplay/TestGrid/AttackZoneHighlightController.cs` + `AttackZoneCalculator.cs`): add an entirely separate visual (own `GameObject`/`MeshRenderer`/material — a red border frame, `Border_North`/`South`/`East`/`West` as four independently-toggleable child strips, sitting just above the cell's `Visual` cube) plus two new `GameObjectActivatorHighlighter`s (`MarkAsAttackZone`/`UnMarkAttackZone`, added to the prefab the same way `MarkAsSelected` etc. already are) targeting the parent, and drive it **directly** via `Highlighter.Apply()` from a project controller that subscribes to `Unit.UnitSelected`/`UnitDeselected` externally (same non-invasive hook `TacticalCameraController` already uses) — never going through `Cell`/`ICellManager` at all, so it can't conflict with TBSF's own 4-slot system. Recompute reachable cells yourself in the handler (`unit.CachePaths(cellManager)` then `GetAvailableDestinations`) rather than trusting `MoveAbilityImpl`'s own cache timing — `GridStateUnitSelected.OnStateEnter` fires `UnitSelected` *before* it runs each ability's `OnAbilitySelected`, so the framework's own cache isn't populated yet when your handler runs.

**`MarkAsHighlighted`/`UnMark` are the one pair of `Cell`'s 4 slots that's actually a live, reusable hover hook — unlike the other three, it doesn't need a parallel system.** `GridState.OnCellHighlighted`/`OnCellDehighlighted` (the *base* class, so this runs in every grid state, selected or not) unconditionally calls `CellManager.MarkAsHighlighted(cell)` / `UnMarkAsHighlighted(cell)` on every mouse hover/unhover — confirmed by reading the call site directly, not assumed. Two things worth knowing before wiring a new visual onto it: (1) `UnMarkAsHighlighted(cell)` doesn't call a dedicated "unhighlight" method — `RegularCellManager` maps it straight to `cell.UnMark()`, the same generic reset used by every other slot. This looks like it should stomp a cell's Reachable/Path color on mouse-out, but `MoveAbilityImpl.OnCellDehighlighted` re-applies `MarkAsReachable` (and repaints the whole `_currentPath`) right after, specifically to undo that — the two-step sequence is deliberate, not a race to work around. (2) Adding a new `Highlighter` component (e.g. a second `GameObjectActivatorHighlighter`) as a sibling on the `MarkAsHighlighted`/`UnMark` child GameObject does **nothing** by itself — `Cell._markAsHighlightedFn`/`_unMarkFn` are explicit `SerializedProperty` reference lists on the `Cell` component, not "every Highlighter found under this named child." The new component must be appended into that list too (`SerializedObject` on the `Cell`, `InsertArrayElementAtIndex` + set `objectReferenceValue`) or it's simply never invoked despite compiling and looking wired correctly in the hierarchy. Used for the hover cursor (thin frame + floating diamond, `HoverCursorVisual`): added the new visual as a sibling of `Visual`/`AttackZoneVisual`, added a `GameObjectActivatorHighlighter` to the existing `MarkAsHighlighted` slot (activate) and `UnMark` slot (deactivate) — appended into both lists — and zeroed the old demo `RendererHighlighter`'s alpha on `MarkAsHighlighted` (it used to re-tint the shared `Visual` fill on every hover, which fights a frame-based cursor concept). No new controller class needed, unlike the attack-zone overlay below, precisely because this slot already had a live, unconditional TBSF caller.

**Neutering a shared-renderer highlighter slot only "does nothing" if it's removed from the list, not just zeroed to alpha 0 — a zeroed `RendererHighlighter` still overwrites whatever color was already there.** Follow-up to the hover-cursor work above: TBSF's stock `MarkAsPath` slot recolors `Visual` green on every hover of an in-range cell (`MoveAbilityImpl.OnCellHighlighted` → `MarkAsPath`), which fires *after* `MarkAsHighlighted` in the same event (`GridStateUnitSelected.OnCellHighlighted` calls `base.OnCellHighlighted` first, then forwards to abilities) — so `MarkAsPath`'s color is what's actually left on screen. Silencing just `MarkAsPath` (emptying `_markAsPathFn`) is not enough on its own: `MarkAsHighlighted`'s own `RendererHighlighter`, even set to alpha 0, still calls `SetPropertyBlock` and stomps whatever `MarkAsReachable` had painted earlier — normally masked because `MarkAsPath` repainted right after it, but with `MarkAsPath` now empty, that stomp becomes the final, visible state. The real fix was removing the `RendererHighlighter` from **both** `_markAsHighlightedFn` and `_markAsPathFn` (via `SerializedObject` array surgery, then `Object.DestroyImmediate` on the now-unused components) so neither step touches `Visual`'s color at all — the cell keeps whatever `MarkAsReachable`/`MarkAsAttackZone` last painted it, hover feedback comes entirely from `HoverCursorVisual`. Lesson: when planning to "quiet down" one highlighter in a shared-renderer chain, trace what runs *after* it in the same event, not just what it does in isolation.

**Per-cell border highlighting on a contiguous zone must be edge-aware, or it renders as a solid grid, not a contour.** The first version of the attack-zone overlay above turned on all 4 border strips on every zone cell uniformly. For a zone spanning dozens of contiguous cells that's visually indistinguishable from "every cell in range has its own box drawn around it" — internal edges between two adjacent in-zone cells just look like ordinary grid lines, so the *intended* outer contour gets lost in what reads as a solid red mesh over the whole area. The fix (now in `AttackZoneHighlightController.ConfigureBorderEdges`): for each zone cell, check each of the 4 neighbor coordinates against the zone's own coordinate set and only enable the border segment facing a neighbor that is *not* in the zone (including grid edges/gaps, where the neighbor doesn't exist at all) — a classic "only draw the boundary edge" rule. This is a property of the visual only; it doesn't change what `AttackZoneCalculator` computes, only which of the 4 pre-built strips light up per cell.

**Two coplanar opaque surfaces at the same world height z-fight, and it can look exactly like a texture/material problem.** `TestSquareCell`'s `Visual` cube used to sit with its top face flush at the cell's pivot height (local Y `-0.5`, cube height 1) — i.e. exactly level with the ground platform surface underneath it once cells are placed via `HeightAwareGridBuilder`. The result was inconsistent, blob-shaped, iridescent-looking patches on the platforms that shifted between otherwise-identical screenshots — trying to fix it as a specular/GI issue (zeroing `_Smoothness`/`_Metallic` on the platform material) did nothing, because the real cause was the renderer depth buffer arbitrarily flip-flopping between two triangles occupying the same depth at different pixels. Confirmed by ruling out shadows (already off) and checking bounds (no actual mesh overlap — the two surfaces are literally coincident, not overlapping). Fixed by lifting `Visual`'s local Y from `-0.5` to `-0.49` in the prefab (a 1 cm gap, invisible at gameplay camera distances) while leaving the cell's pivot/collider — and therefore `HeightAwareGridBuilder`'s raycast target height — untouched. If a flat surface ever shows unstable, patchy, screenshot-to-screenshot-inconsistent shading and material tweaks don't move it, suspect two surfaces sharing a height before reaching for a lighting explanation.

**The same coincident-surface pattern that causes visual z-fighting also causes physics-raycast ties — and `PhysicsRaycaster` has no tie-break, so the outcome flips with camera angle.** `LowerGround`/`UpperGround`/`BridgeDeck` (the decorative terrain meshes, not the cells) each carry their own single `BoxCollider` on the `Ground` layer, sized to cover the whole platform — and its top face sits exactly coincident with each `Cell`'s own `BoxCollider` top face (confirmed to 6 decimal places via `Physics.RaycastAll`: identical distance, identical hit point). Symptom: hovering/clicking some in-range cells silently did nothing — no `HoverCursorVisual`, no move — while other cells on the same platform worked fine; rotating the camera "fixed" one specific cell but broke others. Root cause confirmed two ways: (1) exact-distance ties between `Cell` and terrain colliders, and (2) a live camera-angle sweep on one fixed cell showing the winner of the tie flip between `Cell` and `LowerGround` purely as a function of ray direction, with zero change to actual distances — `RaycastAll`'s ordering for bit-identical hits isn't stable across ray angles. (`CinemachineDeoccluder` was suspected and ruled out empirically — toggling it with the camera transform pinned produced identical raycast results; it only ever repositions the vcam, never touches `Physics.RaycastAll`/`EventSystem`.) Fixed the same way as the analogous render bug: raised `TestSquareCell`'s `BoxCollider` center from `y: -0.5` to `y: -0.485` (top face 1.5 cm above the terrain collider) so the cell deterministically wins the ray, regardless of angle — same trick as the `Visual` render offset above, just on the physics side instead of the render side. **A second, independent, smaller-scope cause was found and left unfixed by that change:** `PhysicsRaycaster.m_EventMask` was `4294967295` (every layer), so a *unit's own* collider (units sit on `Default`, not `Ground`) could be genuinely nearer than a cell positioned behind it from certain angles, stealing that cell's ray outright (not a tie — a real, closer hit). Narrowed the mask to `257` (`Ground` | `Default` only) to drop the other, definitely-irrelevant layers (`TransparentFX`, `Ignore Raycast`, `Water`, `UI`, `PostProcessing`, `Environment`) from ever intercepting a grid ray — but `Default` itself could **not** be excluded: `GridStateAwaitInput.OnUnitClicked` is the *only* unit-selection path in TBSF (confirmed by reading it directly — `GridState`/`GridStateAwaitInput` have no "clicked cell has a unit standing on it → select the unit" fallback), and it only ever fires from a real raycast hit on the unit's own collider. Excluding `Default` would have silently broken clicking units to select them. **If a future feature needs a direct Physics raycast against units specifically (not through a cell), `PhysicsRaycaster.m_EventMask` on `Test_SyntyOnGrid`'s Main Camera is the first place to check** — it's already deliberately scoped to exactly `Ground | Default` and nothing wider; don't be surprised later why some other layer's clicks don't land.

**Cell highlight fill must be a thin transparent overlay, not opaque 3D geometry — an opaque cube fully occludes the terrain underneath it.** `TestSquareCell`'s `Visual` was originally a built-in Cube mesh with an opaque `Lit` material; every highlighted cell fully hid the ground texture/color beneath it, which reads as flat colored tiles rather than a tactical overlay (contrast: Fire Emblem Three Houses' thin tinted overlay that lets terrain show through). Fixed by swapping the mesh to the built-in Quad (fileID `10210`, rotated 90° on X to face up) and giving it its own project-owned Transparent-surface-type material (`Mat_CellFill.mat` — never reuse the shared URP `Lit.mat` for this, see the next entry), with per-highlighter-state alpha set directly on each `RendererHighlighter`'s `_color.a` rather than a shared material default: idle/unmarked = 0 (fully invisible), reachable/highlighted/path = 0.4–0.45 (terrain clearly visible through the tint). A zero-thickness plane's local position *is* its surface height, unlike the cube's center-based pivot — recompute the z-fighting offset from scratch for any such mesh swap rather than assuming the old cube's offset value still applies. The border/contour overlay (`Mat_AttackZoneOutline.mat`) is kept more opaque (alpha 0.85) than the fill by design, since a contour is meant to read more clearly than the body of the zone it outlines.

**`Unit` prefabs carry their own 5-slot highlighter system mirroring `Cell`'s, and TBSF drives it automatically — a persistent "friendly unit" indicator is standard behavior, not a bug.** `TestPeasantUnit` (cloned from TBSF's `Player1 Unit.prefab`) has a `Highlighters` child with `UnMark`/`MarkAsSelected`/`MarkAsFriendly`/`MarkAsFinished`/`MarkAsTargetable` slots, all `RendererHighlighter`s targeting a shared child renderer (`HighlightMesh`, a flat box at the unit's feet) — the exact same pattern as `Cell`'s 4 slots targeting `Visual`, just for units instead of cells. Confirmed via direct grep: `GridController.cs` calls `UnitManager.MarkAsFriendly(TurnContext.PlayableUnits())` at init and at each turn start — this is unconditional, automatic TBSF behavior for every unit belonging to the player whose turn it is, not something project code or a debug leftover triggers. A scene-level `SetActive(false)` on `HighlightMesh` gets silently overwritten back to `true` the next time Play runs, because the framework re-applies it every session — don't chase this as a persistence bug; the fix has to change what `MarkAsFriendly` actually applies (its `RendererHighlighter` color and/or its target renderer's material), not fight the activation. This indicator was invisible for most of the session purely because `Cell.Visual` used to be an opaque cube that fully covered it from above; converting `Cell.Visual` to a transparent quad (see the two entries above) exposed it for the first time — it was never new, just newly visible. Recolored the shared `HighlightMesh` material to a project-owned transparent one (`Mat_UnitIndicator.mat`, same Transparent-surface recipe as `Mat_CellFill.mat`) and changed `MarkAsFriendly`'s color from TBSF's stock opaque green to a semi-transparent gold (alpha 0.35) to avoid two collisions: green is reserved for a future healer/action-zone color, and blue is already used twice (`MarkAsSelected` + the reachable-zone fill).

**A unit's own cell is a valid distance-0 *source* for attack-range math but must be explicitly excluded as a *candidate*, or it always survives a "zone minus reachable" subtraction.** `AttackZoneCalculator.ComputeAttackZone` adds `unit.CurrentCell` to `sourceCells` (correctly - staying put is a valid attack position) and then, for every candidate cell, includes it in the zone if `source.GetDistance(candidate) <= AttackRange` for *any* source - since `GetDistance(cell, cell) == 0`, the unit's own cell always satisfies this against itself and lands in the raw zone. The caller (`AttackZoneHighlightController`) then computes `attackOnly = zone - reachable` to keep the reachable (blue) and attack-only (red) fills mutually exclusive - but TBSF's own `GetAvailableDestinations` already excludes the unit's occupied cell from `reachable` (it's taken), so the unit's own cell was never in `reachable` to be subtracted out, and survives into `attackOnly` looking like a valid attack target on itself. Fixed with a one-line `zone.Remove(unit.CurrentCell)` at the end of `ComputeAttackZone`, right before returning - excluding it from the *result* while still using it as a *source* are two different, independently-necessary steps.

**A "two materials overlapping" bug report can be a pure color-mixing illusion with zero data overlap - verify by disabling layers one at a time, in the actual runtime scene, before touching any set-logic code.** Reported as "purple cells at the reachable/attack-zone boundary, like both materials are rendering at once." Rigorous elimination proved otherwise: disabled `AttackZoneVisual`'s Fill quad entirely (purple persisted) - disabled every border strip on every cell (purple persisted) - only disabling `Cell.Visual` itself (TBSF's own native reachable-fill renderer) made it disappear. Bisecting further isolated it to exactly two cells: the bridge deck tiles at the elevation gap. Root cause confirmed by reading the bridge material directly: `Mat_BridgeDeck._BaseColor = (0.45, 0.32, 0.18)` (warm brown) - alpha-blending the reachable fill's blue (~(0.1, 0.35, 1), alpha 0.4) over that base color arithmetically lands around (0.31, 0.33, 0.51), a genuinely violet/purple RGB triple, purely from `src*alpha + dst*(1-alpha)` math. No cell was ever double-marked - confirmed independently by cross-checking every cell's `AttackZoneVisual`/`ReachableZoneBorder` active state against a fresh `GetAvailableDestinations` call, zero mismatches, both before and after the "purple" reproduced. **The lesson generalizes the session's established "verify visually, not via state readback" principle one step further: even a live visual symptom needs elimination testing (toggle each rendering layer off one at a time and re-screenshot) before assuming it maps to the set-logic layer just because that's the code that was touched most recently** - here the actual fix, if wanted, belongs in color/material tuning (e.g. a brighter or higher-alpha overlay that stays legible over non-neutral terrain colors), not in `AttackZoneCalculator` or the highlight controller, both of which were already provably correct.

**Synty's Fantasy Warrior HUD panel/background sprites (`Assets/Synty/InterfaceFantasyWarriorHUD/Sprites/HUD/*.png`) are plain white shapes meant to be tinted via the `Image.color` property, not pre-colored textures.** Assigning one of these (e.g. `SPR_HUD_FantasyWarrior_Box_Small_Parchment_01`) to a UI `Image` with the default white color renders as an unstyled flat white rectangle with no visible border/parchment detail — looks exactly like a broken sprite reference, but the sprite, its import settings (`textureType=Sprite`, correct 9-slice border), and the Image component were all confirmed correctly configured. Confirmed by opening the raw PNG directly: it really is a white silhouette. Setting a warm brown tint (e.g. `(0.35, 0.24, 0.14, 0.92)`) immediately reveals the intended parchment-scroll shape and border detail. Any hand-built panel background using this pack's shape sprites needs an explicit tint; prefab-assembled pieces (buttons, health bars, labels) don't have this problem since their sprites/colors are already set up correctly inside the prefab.

**A plain field write on a prefab *instance* component doesn't persist through `EditorSceneManager.SaveScene()` unless the change is registered as a dirty/undo operation first.** Setting `unit.DisplayName = "..."` directly via script on a scene GameObject that's a prefab instance, then calling `SaveScene()`, silently produces a scene file with no trace of the change - confirmed by grepping the saved `.unity` file for the field name and finding nothing. Unity tracks prefab-instance field changes as explicit "modification" entries (`m_Modifications` in the serialized scene), and a bare assignment doesn't register one. Wrapping the same assignment in `Undo.RecordObject(component, "...")` + `EditorUtility.SetDirty(component)` before `SaveScene()` fixes it - confirmed the modification then appears in the saved file. This is specific to *prefab instances*; plain (non-prefab) GameObjects created fresh via script don't need this. Also applies to Play Mode: any change made to scene state while `IsPlaying` is discarded on Stop regardless of dirty-marking - editor-time tweaks (tinting, repositioning) must be done and saved in Edit Mode, not verified-and-left-in Play Mode.

**`Test_SyntyOnGrid`'s `PlayerManager` has exactly one registered `IPlayer` (a `HumanPlayer`, `PlayerNumber` 0) despite two units with different `PlayerNumber`s existing on the grid.** `TestEnemyUnit` (`PlayerNumber` 1) is a combat target, not a second turn-cycling player - confirmed via `gridController.PlayerManager.GetPlayers()` returning a single entry. `SubsequentTurnResolverImpl` computes the next player as `(current + 1) % numberOfPlayers`, so with `numberOfPlayers == 1` this always resolves back to player 0 - calling `GridController.EndTurn()` is a structural no-op as far as *whose turn it is* goes, confirmed by tracing every `TurnStarted` invocation during a real `EndTurn()` call and seeing only `PlayerNumber == 0`, never 1. Any UI/logic that expects to observe an actual "enemy turn" state in this scene (a turn indicator, an AI-turn banner, etc.) needs a second registered player added to `PlayerManager` first - this is a real scene-configuration gap, not a bug in code that reads `TurnContext.CurrentPlayer`.

**Never edit any asset under a `Packages/...` path, even by accident.** `Packages/com.unity.render-pipelines.universal/Runtime/Materials/Lit.mat` looks like an ordinary project material reference but is actually Unity's own shared, immutable builtin-package asset — it was unknowingly wired directly into `TestSquareCell`'s `Visual` renderer since an early session. Editing it via script (`SetSurfaceType` + `EditorUtility.SetDirty` + `AssetDatabase.SaveAssets()`) corrupted the shared file in place, which broke Unity's package resolution project-wide and repeatedly forced the Editor into Safe Mode. `AssetDatabase.ImportAsset(..., ForceUpdate)` does **not** revert a corrupted builtin package asset, and deleting `Library/PackageCache` to force re-resolution is **not safe** — it wipes the cache for every `"source": "builtin"` package at once (there were 47 in this project), and Unity's automatic symlink/resolution mechanism reliably rebuilds `"source": "registry"` packages (e.g. Cinemachine) but not `"builtin"` ones, which can be left permanently unresolved across multiple full Editor restarts. The only fix that worked: copy each affected package folder directly from the Editor installation's `Data/Resources/PackageManager/BuiltInPackages/<pkg>` into the project's own `Packages/<pkg>/` as a real embedded copy, bypassing the cache entirely. **Practical rule: before scripting any edit to a material/asset, confirm its path starts with `Assets/...`, not `Packages/...`, first** — if a prefab's renderer references something under `Packages/`, treat that as a bug to fix (point it at a project-owned copy) rather than a target to edit in place. (Known trade-off from this incident's recovery: those 47 packages are now embedded copies rather than resolving normally, so they won't auto-update with the Unity version — worth a proper Package Manager cleanup once the project is stable, not urgent.)

**General principle: reading runtime rendering/animation state back through an Editor-tooling API is not trustworthy.** Two confirmed cases so far: `AnimationMode.SampleAnimationClip` does not run the full Humanoid retargeting pipeline and can report values with no relationship to actual playback (reported ~900–1950°/sec on a clip that plays back smoothly — cost a full session chasing a fake "corrupted mocap" theory). `Renderer.GetPropertyBlock()` read via Unity MCP's `RunCommand` tool likewise does not reliably reflect actual rendering state (returned `(0,0,0,0)` garbage even when the real render was correct, confirmed via isolation including a manual inline `SetPropertyBlock`/`GetPropertyBlock` roundtrip that DID work correctly). In both cases the underlying runtime behavior was fine — only the Editor-tooling readback lied. **Rule: verify actual rendering or animation state visually (a screenshot via `Unity_SceneView_CaptureMultiAngleSceneView`/`Unity_Camera_Capture`, or live per-frame sampling from a running `MonoBehaviour` in Play Mode), never by reading it back through an Editor-only introspection API.**

### Namespace and folder convention

Project code follows a `Fire.<Layer>.<Feature>` namespace pattern, with folders mirroring it exactly:
- `Assets/_Project/Scripts/<Layer>/<Feature>/` → namespace `Fire.<Layer>.<Feature>` (e.g. `Assets/_Project/Scripts/UI/Scroll/` → `Fire.UI.Scroll`)
- `Assets/_Project/Editor/<Feature>/` → namespace `Fire.EditorTools.<Feature>` for the editor-only counterpart of a feature (e.g. `Assets/_Project/Editor/Scroll/` → `Fire.EditorTools.Scroll`)

Follow this pairing when adding new features: runtime code under `Scripts/<Layer>/<Feature>`, editor tooling for it under `Editor/<Feature>`.

Other observed conventions: public fields (not `[SerializeField] private`) are used for Inspector wiring; UI/content strings are Russian while all code/identifiers are English — this is intentional bilingual content, not a mistake.

### The Scroll data model

The only implemented system today is a read-only UI mockup for a "Manor Scroll" record-keeping mechanic (medieval manorial-court roll flavor), living in `Assets/_Project/Scripts/UI/Scroll/`:

- **`ScrollRecordData.cs`** — the data model. `ScrollRecordData` is a plain `[Serializable]` C# class (not a `ScriptableObject`) holding `Name`, `Manor`, `Status` (`ScrollStatus` enum: Villein/Cottar/Famulus/Dependent/Freeholder), `DependentOn`, `Holding`, `Rent`, `WeekWorkDays`, `Debts`, `Amercements`, and `Condition` (`ScrollCondition` enum: Intact/Burned/Rewritten). `ScrollRecordSeedData.GetSample()` provides hardcoded placeholder records pending the real data from the external design doc.
- **`ScrollWireframeController.cs`** — populates the record list from seed data, handles selection, and renders a detail panel. Key mechanic: burning a record (`ScrollCondition.Burned`) redacts a character's labor obligations/debts/amercements while preserving identity facts (name, manor, holding, rent, dependent relationships) — a soft-redaction mechanic, not a delete. Has a debug-only restore toggle for testing the burn/restore cycle.
- **`RecordListItem.cs`** — binds one `ScrollRecordData` to a list row (name/manor/status + a colored condition indicator: gray/red/gold for Intact/Burned/Rewritten) and forwards clicks back to the controller via an `Action<ScrollRecordData>` callback.

Known gap: `ScrollStatus` has no value that fits dependent female records (e.g. a wife/daughter tracked only via `DependentOn`) — this has come up before as a modeling gap worth resolving before building further on top of the enum. **Do not resolve this unilaterally** by adding a new enum value — the authoritative Scroll format lives in the external design doc and should settle this; adding a guessed value now risks diverging from it.

The Scroll record format itself is likewise not fully specified in this repo: `ScrollRecordSeedData.GetSample()` is placeholder data, not the spec. The real format lives at `E:\FireObsidian\Fire\Docs\Narrative\Scroll_Record_Format.md`, which is outside this repo and not visible to you. If a task requires the authoritative format (new fields, status values, redaction rules), ask the user to paste the relevant section rather than inferring it from the seed data.

Known future seam, deliberately not bridged yet: `TestGridUnit.DisplayName` (combat HUD's unit name) and `ScrollRecordData.Name` are two separate "what is this character called" concepts — combat units and Scroll records don't yet represent the same characters, and unifying them is a real future task, not an oversight.

## Git conventions

Unity `.meta` files must be committed alongside the assets they describe. Never delete or regenerate `.meta` files to resolve conflicts — doing so breaks GUID references across scenes and prefabs.

Binary assets (models, textures, audio, fonts, archives, etc.) are tracked via **Git LFS**, configured in `.gitattributes` (the standard Unity gitattributes template). `.meta`, `.cs`, `.asset`, `.prefab`, `.unity`, and other Unity YAML/text files are excluded from LFS and stay in regular git. After cloning, run `git lfs install` once per machine before the first checkout that touches LFS-tracked files (e.g. the Synty/TBSFramework/audio asset packs).

This split relies on `.unity`/`.prefab`/`.asset` actually being text — confirmed: `Edit > Project Settings > Editor > Asset Serialization > Mode` is set to **Force Text** (`ProjectSettings/EditorSettings.asset` → `m_SerializationMode: 2`). If this ever gets changed to Mixed or Binary, the LFS split above stops paying off — no space savings and no readable diffs.
